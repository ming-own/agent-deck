## 3.2 实际对照

在「Agent 会话」的两个新节点使用 GPT-6-Luna，均从空历史开始，角色、指令留空，未勾选技能或工具。两个节点依次收到相同的双人排期题。标准执行 v1.0.0 直接返回排期，用时 9.7 秒；先计划、再执行 v1.1.0 先保存 5 个步骤，然后带着计划完成任务，用时 12.1 秒。两者均给出 7 小时的可行排期，且用关键路径 A → C → E（2 + 4 + 1 小时）证明最优。耗时取本次运行的起止时间。

## 4 画布验收

在桌面端打开同一 Space 的「画布验收 · 研究」和「画布验收 · 审查」两个区域。研究区域有两个 Agent，分别使用标准执行和先计划、再执行。拖动两个区域中的节点、用方向键微调位置后，重新载入桌面界面，两个节点的坐标、缩放、视角及审查员角色均与保存时一致。节点位置写入运行后端的 SQLite，视角按当前设备、账号和入口 Session 保存。

## 5.1 任务续聊验收

在「画布验收 · 研究」的「资料整理」节点，用 GPT-6-Luna 分别记录方案 A 的「松石-37，18」和方案 B 的「琥珀-82，64」。重启本地后端、重新打开会话后，先 B 后 A 发送同一个无提示追问。B 回答「琥珀-82，64」，A 回答「松石-37，18」。每个任务各有两轮记录。

## 5.2 回答转交验收

「资料整理」在「物料清单 · 转交验收」回答“第一版：成本 120 元，交期 7 天。”。将该轮交给「研究提纲」的「成本复核 · 转交验收」任务，补充“只看成本。只输出成本金额，不写交期。”并确认，接收节点返回“120 元”。上游重新回答“第二版：成本 195 元，交期 9 天。”后，重新打开下游任务，展开“引用的回答”仍能查到第一版原文、来源节点与任务、完成时间和同一个来源轮次编号。

## 6.1 路由节点验收

每个 Session 的画布区域内置一个路由节点。画布和 Agent 任务都能发起消息，按消息编号去重。从投递记录补充说明时沿用原目标任务及回传地址。成功结果进入发起处的投递记录；从 Agent 任务发起时，该任务下一轮也能读取这些结果。

桌面实测中，「研究提纲 / 路由验收 · 发起」向「资料整理」发起 A、B 两个任务。并发提交同一条 A 消息两次，两个响应的消息、任务和运行编号一致，只执行一轮。A 返回“青竹 16”，B 返回“白榆 73”。从 A 的记录补充“数量加 5”，得到“青竹 21”。重启后发起任务可查到三条回执，并用三条回传结果回答“青竹 21、白榆 73”。

## 6.2 条件分支与汇总验收

在画布的「路由节点 → 并行分支」中配置 1–8 条分支。关键词留空表示始终运行，否则对消息做不区分大小写的字面匹配；所有命中的分支并行，各自在指定 Agent 的新任务中执行。再次配置时沿用上次提交的分支和汇总规则。没有分支命中时只记一条记录，不创建任务。汇总可要求所有命中分支成功，或等所有命中分支结束并纳入失败状态。中断恢复和重试留给 6.3。

2026-11-05 在「画布验收 · 研究」用两个 Agent 审查同一条预约规则。并发安全审查运行于 16:56:06.186–16:56:10.098，使用体验审查运行于 16:56:06.186–16:56:13.118；重叠约 3.9 秒。最后一个结果写入后，汇总于 16:56:13.122 启动，给出两项建议：原子扣减余量、成功提示展示预约时间。桌面并发投递同一事件两次，两个响应的分支运行编号一致，最终只有两个审查任务和一次汇总。

## 6.3 队列、停止和恢复验收

Agent 对话和路由补充消息共用目标任务的队列。每条补充作为独立一轮，轮到时读取已完成的对话历史。可以取消排队消息、停止当前轮次或停止整组分支。停止当前轮次或重启运行后端后，在目标任务中重新确认待执行消息和工具权限。分支记录保留当轮结果，已完成的汇总仍引用当时收齐的各轮回答。

在「画布验收 · 研究」的预约审查中，并发审查成功，体验审查因测试 Skill 不可用而失败。重启本机后端，移除测试 Skill，再从原记录重试。先前授权的「查询 UTC 时间」初始未选，手动勾选后并发投递两次同一确认请求。两次均成功返回，成功分支保留原运行，失败分支在原任务中新增一次尝试，两个结果收齐后生成一条汇总。另在同一任务连续提交“记住 17”“加 5”“翻倍”，后两条进入队列，依次得到 17、22、44。

恢复以已保存的任务和轮次为边界。模型请求被中断时，从该轮输入重新执行。全部分支已经完成、尚未启动汇总时，可以单独继续汇总。每次恢复分别确认各分支和汇总的本轮授权。

## 7–8　团队复用与模板版本验收

在「画布验收 · 研究」将预约规则的并发审查、体验审查和结果汇总保存成「预约双审团队」v1。通过「创意工坊」添加到「画布验收 · 审查」后，输入带“甲17”的任务，两位 Worker 分别给出意见，再由汇总节点返回两条建议。修改该实例的体验审查员，将模型从 GPT-6-Luna 换成 GPT-6.1-Sol，再保存为 v2。

随后并行运行两项独立任务：研究 Session 的 v1 两位 Worker 均使用 Luna，输出保留“乙29”；审查 Session 的外层团队将 v2 作为分支，由 Sol 参与内层审查，最终结果保留“丙41”。两个任务的节点、历史和汇总记录相互独立。模板保存配置、路由和模型引用；不会带走历史、密钥和单轮授权。工坊为当前账号的本地模板库。

在路由的「并行分支」可以直接保存尚未运行的配置；在「创意工坊 → 保存为模板」也可以选择已有节点或路由记录。修改实例后可以从其当前版本派生新的模板；基于最新版的实例还可以保存下一版本。已有版本和已添加的实例保留原配置。

## 贯穿各阶段的边界

Session 划定画布区域和记录归属；节点配置模型、角色、Skills、工具权限与 Harness；任务上下文接收属于同一件工作的输入、上游结果和历史；每轮运行记录当时使用的配置与授权。传递结果或补充背景时，接收节点仍需按自己的权限执行。

Super-Agent 风格的 Workforce 是阶段 7 的组合验收案例。先验证画布内的路由与恢复；GitHub、飞书等外部事件源在需要时作为独立接入项评估。

## 画布直接编排

已支持任意同 Session 节点间的持久连线和指定回答转交。从画布直接打开节点配置、继续其任务，或展开和修改 Workforce 的分支与汇总。手动连线不自动运行整张图。[设计审查、操作方式和两项桌面验收](agentdeck-canvas-audit.md)。

### 画布试运行

在任意 Agent 卡片点 ▶，输入任务、查看路径并点击「试运行」。按启动时的连线逐个执行；每个节点在自己的新任务中使用自己的模型和配置，下游引用上游刚完成的回答快照。节点显示最近一次试运行的状态及结果摘要，点击可读全文。普通对话和「转交回答」仍由用户决定何时递交。这一版支持最长 32 个节点的单向路径；遇到分叉或循环会在启动前提示，上游失败不会启动下游。

在「自由编排 · 试用」实测，A · 提案（GPT-6-Luna）整理青竹活动预算 42 元及已用 17 元，B · 复核（GPT-6.1-Sol）自动收到当轮回答，算出余额 25 元。观察到 A 运行 / B 等待、A 完成 / B 运行、两者完成三个状态。刷新后仍可打开全文，数据库记录确认 B 引用的轮次和正文均与 A 一致。
